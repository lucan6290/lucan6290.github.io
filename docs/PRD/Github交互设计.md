# GitHub 同步与发布边界

> 更新：2026-10-29。当前前端没有内置 Git 发布后台；本文约定现行 Git 操作和后续产品化边界，不授权实际同步、提交或发布。

## 当前职责

- 本地 Markdown 是内容事实源，Git 保存用户选择的代码、内容及文档变更。
- 读者站点运行静态构建产物，不在网页中执行 Git、管理凭据或上传私钥。
- 当前工作流已配置为测试、构建并发布 `frontend/dist/`，部署路径来自 GitHub Pages 元数据；静态文章入口和线上发布结果按 [部署计划](../superpowers/plans/2026-10-29-github-pages-frontend.md) 单独验证，本地实现不等于线上已生效。

## 提交和推送

1. 先 `git fetch`，检查工作区、当前分支与远端关系。
2. 核对本任务的具体文件和验证结果，取得明确提交授权。
3. 精确暂存相关文件，一次提交只包含一个功能或修复。
4. 用 `类型: 中文简要描述` 提交，核对提交记录及剩余工作区。
5. 只有用户明确要求推送时才推送，并核对远端提交。

禁止笼统暂存整个工作区。不得自动 pull、rebase、处理冲突或改写历史来完成提交；需要这些操作时先说明当前分支状态并取得用户明确同意。

## 后续产品化需求

如果用户另外批准实现 Git 管理功能，应将「发布所选变更」「更新工作区」「连接配置」区分为明确动作，并先定义接口与验收。

- 提交范围应展示具体文件，排除未选中的用户变更。
- 分支名称来自实际仓库或用户选择，不假定固定内容备份分支。
- 同步前提供工作区及分支关系，出现冲突停止并交由用户处理。
- 凭据采用明确权限与最小范围，私钥不在页面显示或写入仓库。
- 服务器更新、部署及重启服务需要独立确认，不能与保存文章混为一个操作。

上述后台能力目前不属于当前前端已实现功能。若引入运行时服务，先按 [后端边界](../BACKEND_CONVENTION.md) 和 [契约](../API_CONTRACT.md) 设计。

公共权限与完整 Git 规范见 [GLOBAL_STANDARDS.md](../GLOBAL_STANDARDS.md)。
