# 全局开发规范

> 更新日期：2026-10-29。适用范围：当前工程的实现、内容和文档维护。

## 开发原则

- 每次修改必须同时改善用户体验、开发体验和 AI Agent 使用体验，并通过与改动相符的验证确保不破坏现有功能。
- 当前项目处于开发阶段，禁止为了历史数据增加兼容代码分支。不符合当前规范的旧数据可以直接丢弃或替换，使用新规范数据测试。
- 用最少的代码完成已确认需求；优先复用已有组件、内容扫描与路径工具。
- 只修改与任务直接相关的文件，不进行顺手重构、批量格式化或无关清理。

## 修改权限与工作区

- 修改业务代码前必须取得用户明确实施指令；分析、定位和设计不等于代码修改授权。
- 纯文档可按用户要求创建或更新；新代码文件与目录必须有明确任务依据。
- 用户已授予的任务权限持续有效，按其具体范围执行；提交和推送须分别获得明确授权。
- 先检查工作区，保护用户已有改动；不要覆盖、回滚或提交无关文件。
- `frontend/content/` 是唯一内容事实源；禁止编辑 `frontend/src/generated/`、`frontend/dist/` 来实现功能。

## 开始修改前

1. 阅读 [frontend/README.md](../frontend/README.md)，再按 [文档索引](DOCUMENTATION_INDEX.md) 定位任务规范。
2. 明确目标、范围和验收方式；多步骤任务提供简短计划。
3. 先发现已有实现，再决定是否新增。涉及字段、路由或生成数据时先核对 [内容契约](API_CONTRACT.md)。
4. `.codegraph/` 存在时，理解或定位代码先用 CodeGraph；不存在时不自行建立索引。
5. 对事实、假设和待确定事项作明确区分，发现错误前提时直接说明。

## 运行与工具

- 当前前端使用 pnpm；开发及本地构建预览固定为 `http://127.0.0.1:3400/`，不得通过换端口规避占用。
- 启动前检查端口并核对进程来源；只停止已确认的本项目服务。开发服务和预览不能同时占用 3400。
- 测试要求 Node.js 22.18+ 或 24+；实际命令见 [README](../frontend/README.md)。
- 普通文本读取不得传入 PDF 专用的 `pages` 参数。
- 访问国外地址遇到网络问题时使用 `127.0.0.1:7890`；国内网站不使用代理。

## 验证与三种体验

| 维度 | 检查重点 |
| --- | --- |
| 用户体验 | 分类可到达、内容可读、图片可见、目录可跳转、窄屏和键盘操作可用 |
| 开发体验 | 修改入口明确、事实源单一、无需手工同步导航、生成过程可复现 |
| AI Agent 使用体验 | 文档与代码一致、字段和路径可定位、授权及验证结果清楚 |

- 对行为改动运行相关回归测试与必要的构建；交互或视觉改动检查实际浏览器页面。
- 文档和低影响内容调整检查事实、链接与差异，不为凑验证而添加重复实现的测试。
- 验证通过后，仅在出现新改动、失败或未解决风险时重复或扩大检查。
- 报告实际命令结果及仍存在的限制，不把“本地实现”“提交”和“线上生效”混为一谈。

## Git 约定

- 未获用户明确指令，不自动提交或推送。
- 提交前执行 `git fetch`、`git status`、`git branch -vv` 检查远端状态；`pull`、rebase 等改变工作区或历史的同步操作须另获明确同意。
- 只暂存和提交明确列出的相关文件；每次提交仅包含一个功能或修复。
- 提交格式：`类型: 中文简要描述`，英文冒号后一个空格，描述不超过 30 字。
- 类型使用 `feat`、`fix`、`docs`、`style`、`refactor`、`test` 或 `chore`。
- 提交后核对提交记录与剩余工作区；推送后再核对远端提交。
