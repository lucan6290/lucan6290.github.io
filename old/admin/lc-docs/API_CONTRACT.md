| 角色 | 定位 |

契约优先原则：主契约文档 > 后端代码 > OpenAPI > 前端调用 > 测试用例。若代码/OpenAPI 与主契约不一致，视为后端待修复问题，而非前端兼容依据。

> 本项目有既有的、持续维护的主契约文档，治理不另造第二套契约源；本文件只做「约定汇总 + 指向」，接口的字段级明细以 `admin/docs/管理员后端接口文档.md` 为准。

## 2. 基础约定

- Base URL：`http://127.0.0.1:18000`
- 版本前缀：`/api/v1`
- Content-Type：JSON（文件上传用 `multipart/form-data`）
- OpenAPI 快照：`/docs` 与 `/openapi.json`

## 2.1 字段命名（DECLARED）

> 来源：project_decision（用户决策）

- **API 字段统一使用 `snake_case`**（与 Python/DB 一致，GitHub/Stripe 风格）。
- 单接口/单项目内不混用 camelCase 与 snakeCase（`mixing_naming_styles_within_api`）。

## 2.2 转换边界

> 来源：profile_default（Skill Technology Profile）

- 字段命名转换（snake_case ↔ camelCase）归属后端 contract boundary，由 Pydantic schema / `alias_generator` 完成。
- 前端直接消费已对齐的 snake_case 契约，不做全局运行时转换。
- 反模式（avoid）：DB 字段直接作为 API 字段（`db_field_directly_as_api_field`）、ORM/文件模型直接作为 API 响应（`orm_leaking_to_api`）。

## 3. 认证与鉴权

- 登录：`POST /api/v1/auth/login` → `{ access_token, expires_at, username }`。
- 鉴权：`Authorization: Bearer <token>`；`<img>` 等场景允许 `access_token` query 参数。
- 公开接口：`GET /api/v1/health`、`POST /api/v1/auth/login`；其余 `/api/v1` 需 token。
- 会话：`GET /api/v1/auth/me`。

## 4. 统一错误响应

```json
{ "code": "article_not_found", "message": "文章不存在。", "request_id": "…", "details": {} }
```

- 常见 HTTP：200 / 201 / 400 / 404 / 409 / 422 / 428 / 500。
- 通用错误码：`request_validation_error`(422)、`internal_error`(500)、`unauthorized`/`invalid_token`(401)。
- 各接口特有错误码见主契约文档对应小节。

## 5. 列表 / 排序 / 分页约定

- 分页：`page`（默认 1）、`page_size`（默认 20，1–100），响应 `{ items, page, page_size, total, has_next }`。
- 排序：`sort` 字段，`-` 前缀降序，多字段逗号分隔；只允许各接口声明的字段，非法返回 `400 invalid_sort_field`。

## 6. 危险操作约定

- 通用字段：`dry_run`（默认 true）、`confirm`（默认 false）。
- 预演返回 `MutationPlanDTO`（`dry_run`、`requires_confirmation`、`changes[]`、`warnings[]`）。
- `dry_run=false` 未 `confirm=true` → `400 confirmation_required`。

## 7. 乐观锁约定

- 读接口返回 `version` + `updated_at`；写接口传 `expected_version`。
- 缺少 `expected_version` → `428 version_required`；不一致 → `409 version_conflict`。

## 9. 跨层字段一致性（强制）

同一业务字段在 Database → Backend → API → Frontend 间保持一致：

```text
Semantic Meaning / Type / Optional / Nullable / Enum / Validation
```

- 字段命名：API 层统一 snake_case（project_decision）；前端类型从契约派生并直接消费 snake_case，如需字段映射仅针对单个接口显式映射（不做全局运行时转换）。
- 层间转换规则显式记录；前后端不一致上报契约评审（Contract Reviewer）。

## 10. 变更兼容性

- 新增响应字段属于非破坏性变更；删除/改字段类型/必填化属于 Breaking Change，需记录兼容性影响与过渡策略。
- 契约变更须同步更新主契约文档的「变更记录」章节。

## 11. HTTP Method 语义

- `GET` 只读查询；`POST` 创建资源或动作型操作；`PUT` 全量更新；`DELETE` 删除；暂不用 `PATCH`。
- 语义不匹配不得混用（如用 GET 执行删除）。

## 12. Nullable 与 Optional 语义

- `Optional`（可选）：字段可缺省（默认值或省略）。
- `Nullable`（可空）：字段可显式为 `null`。
- 两者分别显式声明，前端类型同步标注 `?`（可选）与 `| null`（可空），避免「后端可空但前端当必填」。

## 13. 枚举（Enum）约定

- 枚举值在契约中显式列出并封闭（如 `type: docs | blog`、任务状态 `pending | running | success | failed | cancelled`）。
- 跨层枚举语义一致：DB/后端/API/前端同一枚举含义，存储与传输的转换规则显式记录。

## 14. 时间格式（Datetime）

- 时间统一 ISO 8601 字符串，显式含时区（`2026-06-29T18:00:00+08:00`）。
- blog `date` 至少以 `YYYY-MM-DD` 开头；后端默认 `Asia/Shanghai`；任务时间字段用 `started_at` / `finished_at`。

## 15. 过滤（Filtering）约定

- 列表过滤用独立 query 参数（如 `type`、`keyword`、`tag`、`author`、`category`、`has_issues`）。
- 过滤字段只允许各接口声明的参数；未声明字段的过滤行为以接口文档为准。

## 16. 废弃（Deprecation）约定

- 废弃字段/接口先标记 deprecated 并保留过渡期，不直接删除。
- 主契约文档记录废弃标记、替代方案与移除计划；破坏性移除走契约评审（`contract-review`）。
